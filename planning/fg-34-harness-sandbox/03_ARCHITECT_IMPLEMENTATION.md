## Deployment boundary (D8)

Docker mode requires a daemon the agent can reach and a workspace path the
daemon can bind-mount. `PoolManager` forwards the operator `SANDBOX_*` settings
to each pool agent, sets `BACKEND_URL=http://api:3001` (the root Compose service
name), resolves Docker prerequisites **before** creating the DB agent or
container, and fails the request when `DOCKER_HOST` or a host-visible workspace
root is unresolved. `SANDBOX_REQUIRE=true` without `SANDBOX_MODE=docker` is
rejected by the API at the same point, and a failed create/attach removes the
container and DB agent record. Only Docker-mode agents receive `DOCKER_HOST`
(from `AGENT_DOCKER_HOST` or a TCP `DOCKER_API_URL`) and are attached to an
internal control network shared with the restricted socket proxy; host-mode
agents receive neither and cannot reach the proxy by name. A bare API unix
socket is not passed to pool agents because they do not mount it.

The control network name is project-scoped by default
(`${COMPOSE_PROJECT_NAME}-sandbox-control`) and can be overridden with
`SANDBOX_CONTROL_NETWORK`; this keeps Compose projects and CI jobs on separate
Docker API proxies. The repo volume is explicitly named `vibecode_repos` in
Compose so the API mount, `REPO_VOLUME`, and the inspected mountpoint are the
same volume even with project-prefix naming. A `REPO_VOLUME` override changes the actual
Compose volume name and is resolved consistently by the API mount and
PoolManager; in Compose it must remain a volume name, not a host path (host
paths are supported by the non-Compose runner). An installation that previously
used a project-prefixed volume can copy it once into `vibecode_repos`; the old
compose prefix otherwise leaves that data unused. `PoolManager` creates a missing named volume before
inspecting it, maps the mountpoint to `SANDBOX_HOST_WORKSPACE_ROOT`, and uses
`/repos` as the container root; a host-path `REPO_VOLUME` is used directly and
an explicit root wins. The root Compose proxy enables
create/exec/copy/network/volume/pause operations but is reachable only from the
API and Docker-mode pool agents on the internal control network, not from the
frontend, database, cache, host-mode agents, or the sandbox itself.

The sandbox still receives no Docker socket or `DOCKER_HOST`; only the
supervisor agent talks to the restricted proxy. `SANDBOX_MODE` remains `host`
by default, so Docker mode is opt-in. The proxy can manage
containers/networks/volumes beyond one pool agent's own resources, so the
daemon/proxy is a deployment trust boundary, not a multi-tenant boundary; pool
replacement cleanup is D30. The standalone `agent/docker-compose.yml` stays on
the API network in host mode and needs a host bind at `/repos`
(`REPO_HOST_PATH`) writable by the agent user (uid 100/gid 101), plus
`ROOT_COMPOSE_PROJECT` (or the explicit `VIBECODE_NETWORK`/
`SANDBOX_CONTROL_NETWORK`) matching the root project. Docker mode uses the
`agent/docker-compose.sandbox.yml` overlay, which adds the restricted proxy
network and `DOCKER_HOST`; host mode never joins that network.

OpenCode still runs in the supervisor in slice 1. Only supervisor-driven
install/verification commands go through the sandbox; a prompt-injected
OpenCode `bash` call still executes on the supervisor until the slice-2
bridge. Operator docs state this explicitly.

### Coverage notes

- The prompt labels ticket, planning and repository content as untrusted, states that supervisor instructions and the publishing policy take precedence, and escapes the untrusted-content terminator. The built-in `read`/`grep`/`lsp` tools are disabled; `sandbox_read`/`sandbox_grep` call a loopback workspace bridge that resolves `toRealPath()`, rejects targets outside the workspace and the credential-path denies, and grep never follows symlinks (D18). The built-in `edit`/`write`/`multiedit`/`patch` tools are disabled (OpenCode 1.19.5 maps edit/write/apply_patch to the `edit` action; the extra keys are defense in depth); `sandbox_write`/`sandbox_edit` walk the path through `SecureDirectoryStream` descriptors with NOFOLLOW on every component including the final open, reject symlink targets and credential/VCS/control paths, bound the replacement size before allocation, preserve BOM/CRLF for edits, and serialize writes/edits with a bounded per-file lock, closing D20 where secure directory streams are available and D21's clobbering risk. Read/grep use the same secure open helper. Native Windows or other providers without `SecureDirectoryStream` use a non-atomic canonical fallback in host mode; sandbox mode fails fast at bridge startup, and `SANDBOX_REQUIRE_SECURE_FILE_ACCESS=true` makes host mode fail fast too (D22; host mode is not a security boundary). FIFO targets are rejected before open; a final-component swap can still block an open until a peer opens it (D23 residual). The bash bridge denies a high-confidence subset of credential-file reads, interpreter one-liners, network uploads and `/dev/tcp`; it is a coarse regex denylist, not a shell parser (a `-F` token inside a quoted header value can false-positive, and encoded forms can bypass). The supervisor refuses to publish a guarded-tree changed blob whose content or new path contains a configured credential or a high-confidence credential format; it reads tree blobs directly so `.gitattributes`/binary/`++`-prefix/filename bypasses do not hide content, compares against the base blob so pre-existing fixtures in modified files do not block unrelated edits, compares complete PEM private-key blocks (case-insensitive BEGIN/END detection; exact block comparison, so reformatting/case-changing a pre-existing block counts as new), exposes new gitlink paths to the path scanner, and fails closed on a blob larger than the scan limit. A changed or base blob above the 8 MB scan limit fails closed; raising `HARNESS_MAX_BYTES` above that can reject a large modified file, and a diff-based scan is the future fix. Prompt injection remains probabilistic; the sandbox, secretless env and publishing guard are the boundary (FR8).
- CPU/PID enforcement is asserted through the `docker run` flags; the integration test asserts the memory cgroup bound. A behavioral CPU/PID stress test is deferred to slice 3.
- Supply chain (FR9): every base image in the supervisor, sandbox and proxy Dockerfiles is pinned by digest; `agent/scripts/sandbox-image-security.sh --check-pins` is the deterministic CI gate. The gate matches `FROM` case-insensitively, strips a leading UTF-8 BOM and CRLF, ignores references to earlier build stages and requires the digest on the image token (an inline-comment digest does not count). `--all` runs the same pin check before the SBOM/scan steps. `--sbom` uses syft (SPDX JSON under `agent/target/sbom/`), `--scan` uses trivy or grype with a HIGH/CRITICAL default, and `--all` optionally verifies a cosign signature when `COSIGN_PUBLIC_KEY` is set. CI builds and scans the supervisor, sandbox and proxy images and archives the SBOMs. SBOM/scan tools are optional locally; set `SANDBOX_SCAN_REQUIRED=1` in CI to fail instead of skipping. Scanner semantics differ: trivy uses `--ignore-unfixed` while grype has no equivalent and fails on any matching (including unfixed) finding. Node installs already use `npm ci` when a lockfile exists and `--no-package-lock` otherwise. Lifecycle scripts run inside the sandbox; a repo-profile opt-out is fg-39.
- The disk quota is enforced by a lifetime supervisor watchdog at `SANDBOX_DISK_CHECK_INTERVAL_SECONDS` granularity. Measurement failure (including per-file `visitFileFailed`) fails closed. Unlinked-but-open files are outside the supervisor walk and require a real FS quota (D12).
- The Docker file channel uses distinct non-zero exit codes for guard failures, so a same-UID stdout flood cannot mask them; successful guards also print `OK`/`OK <size>`. Downloads are read with `docker cp container:path -` **without `-L`** through the bounded tar reader, which streams exactly one regular-file entry straight into the temp file (no whole-artifact `byte[]`), enforces the artifact size before the supervisor writes it, and checks an output-completion latch before reading the reader failure, so a pipe that never reaches archive end fails closed and a reader that fails at the edge of the join window cannot be observed as a stale success. The in-container stat check remains defense in depth; the tar stream is authoritative. The no-follow guarantee is final-component only: `docker cp` still resolves intermediate directory symlinks, which the pre-copy `readlink -f` guard normally rejects. A racing same-container process can therefore redirect an intermediate component, but the reachable files are inside the sandbox container (its only host mount is `/workspace`), so this does not expose supervisor secrets (D10).
- Reaping starts with the D9 same-owner pass: the owner label is on sandboxes, proxies and egress networks. D30 adds a safe pool replacement sweep. `PoolManager` sets `SANDBOX_OWNER=pool-<dbAgentId>`, `SANDBOX_POOL_AGENT=true` and `SANDBOX_DAEMON_ID`, and labels its own agent container `vibecode.agent.owner=pool-<dbAgentId>`, keeping numeric `AGENT_ID` for harness bookkeeping. The `pool-` owner prefix is reserved for PoolManager; a manual agent using it fails startup. A pool owner lists managed resources across owners and reaps another `pool-` owner's containers/networks only when no agent container carries that owner label **and** the agent's `docker info` daemon ID matches `SANDBOX_DAEMON_ID`. This covers custom deployments where the API and agent Docker clients point at different daemons: a mismatch or unknown ID skips the sweep safely, and custom socket proxies must allow `INFO=1` for the check. `SANDBOX_POOL_AGENT`/`pool-` owners are PoolManager-only; a manual agent must use a non-pool owner, and an opt-in without the matching agent container label remains unsupported. A live replacement or concurrent agent is therefore never swept; a killed pool agent's resources are cleaned by the next start. Numeric-owner resources from #154–#157 and unlabeled resources created before #154 are not auto-reaped and need a one-time operator cleanup. A stopped agent container counts as live, so its resources wait until it is removed. Two live processes sharing an owner would reap each other's resources, so one live process per owner remains required. Read/list/remove failures are logged and do not block startup; a truncated listing leaves the remainder for the next start.
- A pre-publish `destroy` failure fails the ticket and never stages or pushes; `DockerSandboxRunner.destroy` verifies removal and keeps tracking on failure. `close()` retries tracked containers and retains the shutdown hook while any remain; a hard-killed agent leaves cleanup to the D9 reaper.
- `SANDBOX_NETWORK=allowlist` creates a per-sandbox internal Docker network and a hardened proxy container (read-only rootfs, dropped capabilities, non-root, PID/memory/CPU limits, capped Docker logs). The proxy is attached to the upstream network only after it is healthy, and the sandbox joins only the internal network. It rejects IP literals, localhost, private/link-local/metadata addresses and cloud/test ranges (Azure WireServer, 192.0.0.0/24, 198.18/15, NAT64, 6to4, Teredo, documentation), unapproved ports and non-allowlisted hosts. For CONNECT tunnels it validates the first TLS ClientHello SNI and rejects multiple SNI names, duplicate SNI extensions, extra handshake messages, ECH and missing SNI. CONNECT :80 is rejected; plain HTTP uses per-request absolute-form validation. `SANDBOX_EGRESS_TLS_MODE=terminate` is opt-in: the proxy terminates TLS with a per-run CA, parses HTTP/1.1, enforces `Host == SNI`, rejects ambiguous framing (including chunked-body smuggling), `101`/`Upgrade`, and re-originates with a verified TLS connection; duplicate response headers are preserved. The supervisor reads the proxy CA with bounded `docker exec cat` (docker cp cannot see a tmpfs), pre-checks the sandbox system bundle path, reads a regular bundle through a bounded `docker cp -L ... -` tar stream, validates X.509 CA certificates, builds a combined bundle and writes it into the sandbox tmpfs with bounded `docker exec -i`; a broken/non-regular/oversized/malformed/timed-out source fails creation closed, while a genuinely missing bundle is the CA-only fallback. The default remains `sni-only`, where only the first ClientHello is inspected and TLS renegotiation plus the encrypted inner HTTP Host remain a shared-CDN limitation (D16; default flip is D25). A sandbox that contains a JDK/keytool at creation also gets a copied `$JAVA_HOME/lib/security/cacerts` plus the per-run CA in `/tmp/vibecode-java-truststore`, with `JAVA_HOME` and `JAVA_TOOL_OPTIONS` added to every exec; a missing JDK is logged and leaves Java unsupported, and a JDK installed by a later setup command is not auto-detected. This assumes a standard JDK store with the public default `changeit` password; a custom password fails creation. The truststore is mode 0444 and sandbox-owned, so sandbox code can replace it; it is not a host boundary. An external `SANDBOX_EGRESS_PROXY` is rejected because it would reintroduce direct egress. External DNS is disabled in the sandbox (the proxy is addressed by IP and pinned in `/etc/hosts`), so DNS cannot be used as an untracked exfiltration channel; package managers still work through the proxy. Only denials are logged, rate-limited to 20/second, and Docker log size is capped for both the proxy and the sandbox. Denials are surfaced from `docker logs` when the sandbox is destroyed; live streaming of proxy logs is part of D15. The first-ClientHello probe timeout is configurable via `SANDBOX_EGRESS_PROBE_TIMEOUT_MS`. The proxy runs from the dedicated `SANDBOX_PROXY_IMAGE` (not a repo-specific sandbox image), and the supervisor explicitly clears the gated resolver/loopback/test-port seams in the proxy environment. Terminate mode adds `openssl` and `ca-certificates` to the proxy image; the image remains digest-pinned and scanned.
- The OpenCode bash bridge binds to 127.0.0.1 with a per-run random token and is closed after the prompt. The sandbox has no route to the host loopback. In Docker mode the built-in `bash` and `shell` tools are denied and the global `sandbox_bash` tool forwards to the bridge; this is fail-closed if the custom tool fails to load. The bridge enforces the supervisor command policy and maps supervisor workspace paths to `/workspace`. Host mode keeps the built-in bash tool. Exec requests carry a client request ID and use a bounded 64-entry/10-minute result cache; duplicate IDs return the cached result, conflicting payloads get 409, and missing IDs retain legacy behavior. The `sandbox_bash` client retries a lost response and 502/503/504 with the same ID (three attempts, short backoff) while 400/403/409/500 are not retried. Tests cover in-flight duplicates, 504, TTL expiry, LRU eviction, cwd/timeout fingerprint conflicts, uncached 500s and the 128/129 ID boundary.
- Hostile install/test containment is covered by the real-Docker background-writer, postinstall-like lifecycle, forking-writer and sequential-exec regressions. The post-exec sweep runs five kill passes, then freezes the container, reads the init host PID with `docker inspect`, and verifies the frozen table contains nothing else before thawing. PID 1 is a childless `exec sleep`, so it cannot respawn a child, and execs are serialized per sandbox so one sweep cannot freeze another command. A survivor or unverifiable freeze/table/destroy destroys the sandbox, marks the handle compromised, and fails the exec even after cleanup; `destroy()` then refuses to report the handle as clean for the rest of the runner's lifetime, so the pre-publish gate blocks publishing even when no verification commands ran (D14, #139). CI builds the sandbox image and runs this suite against it (D13); a real npm lifecycle fixture remains future integration coverage.
- `--init` is intentionally not used: PID 1 is `exec sleep 2147483647`, a single childless process, so the frozen quiescence check can preserve exactly the init host PID reported by `docker inspect`. Zombies (which cannot fork) are ignored only when `docker top` provides a state column; any other live process stops the sandbox (D14).
- The integration tests are opt-in locally (`SANDBOX_IT_IMAGE`, plus `SANDBOX_IT_NETWORK`/`SANDBOX_IT_NETWORK_IMAGE` for egress); CI builds the sandbox and proxy images and runs `DockerSandboxRunnerIntegrationTest` against them in the `Sandbox Integration` stage (D13). `PoolManager` wiring is D8: it forwards the sandbox environment, derives `DOCKER_HOST` from the socket proxy, and resolves the repo volume mountpoint for host-visible bind mounts.
- NFR5 (redaction before storage): `VerificationRunner` pattern-redacts captured output (including exception messages) before truncation, and `HarnessTicketProcessor` redacts configured secrets plus high-confidence credential formats before deriving a branch name, posting ticket messages, finishing a durable run with an error, or creating a commit/PR title or PR body. The key/value rule first requires a credential keyword in the identifier via a lookahead, then matches the identifier once with a possessive quantifier. The lookahead prevents a non-credential assignment such as `{"message": "password=supersecret"}` from consuming the nested credential, and the single possessive match keeps repeated keywords linear on hostile input (64 KB/128 KB regressions). An unquoted value is redacted through end-of-line, stopping only at a quote or newline, so `password=supersecret phrase`, `password=super)secret` and non-Bearer authorization schemes are fully redacted; over-redacting adjacent text is preferred to a partial value. Multi-line private-key blocks are redacted before key/value processing so `password=-----BEGIN...` does not leave the block body unredacted. A BEGIN without an END redacts the remaining output. Credential values shorter than eight characters are not redacted by the pattern rules (and configured secrets shorter than eight characters are ignored) to avoid corrupting ordinary output. The publish gate (`SecretLeakGuard`) checks known secrets plus GitHub/OpenAI/AWS (including `ASIA`)/Slack (including `xoxc`/`xoxd`)/Google/JWT tokens and PEM/PGP/SSH2 private-key blocks; Bearer/Basic, URL-userinfo and key/value forms such as `passphrase=` are redaction-only patterns, not publish-gate formats. This is a storage guard, not a sandbox boundary; encoded, split or transformed credentials can still evade pattern matching, and provider-side telemetry is outside this slice. Legacy `TicketProcessor`/`ReviewProcessor` messages are redacted by `ApiService.postMessage`, branch/commit/PR titles by `TicketProcessor` and `GitHubService`, and shipped supervisor log lines by `RedactingPatternLayoutEncoder`. All three read the process-wide `RedactionRegistry`, which receives the resolved provider key and runtime GitHub App tokens (plus env secrets) so a backend-fetched custom key is covered even though it matches no pattern (D19). The FR11 streaming part remains D15.
