# bp-31: TemplateService Redesign — Design

**Status**: planned
**Date created**: 2026-06-27
**Scope**: Backend

## Current State

`TemplateService.js` has a static `ARCHITECT_TEMPLATE_FILES` array with 4 entries:
```javascript
const ARCHITECT_TEMPLATE_FILES = [
  { key: '00_ARCHITECT_CHECKLIST.md', title: 'Pre-Implementation Checklist', required: true },
  { key: '01_ARCHITECT_REQUIREMENT.md', title: 'Requirement', required: true },
  { key: '02_ARCHITECT_DESIGN.md', title: 'Design', required: true },
  { key: '03_ARCHITECT_IMPLEMENTATION.md', title: 'Implementation', required: true },
];
```

The content for each template is generated by `getArchitectTemplateContent(fileKey)` using a simple `templates` object map. The content strings contain placeholder text (`Describe the requirement here.`, `- Assumption 1`, etc.) and lack structured headings like Impact Analysis, Decisions Required, Per-File Action Plan, and Security Considerations.

There is no `04_SPECIFICATION.md` entry. There is no standalone `SPECIFICATION` template type.

## Proposed Solution

### Approach

1. **Expand `ARCHITECT_TEMPLATE_FILES`** to include a 5th entry:
   ```javascript
   { key: '04_SPECIFICATION.md', title: 'Execution Specification', required: true },
   ```

2. **Rewrite each content method** (`00_ARCHITECT_CHECKLIST.md` through `03_ARCHITECT_IMPLEMENTATION.md`) to produce the structured templates defined in DREAM.md. Each template uses real content patterns, section headings, and filler instructions — not placeholder text.

3. **Add new template type**: Create a `SPECIFICATION_TEMPLATE_FILES` constant and `getSpecificationTemplate()` / `getSpecificationTemplateContent()` methods following the existing pattern.

4. **Content design**: Each template section is a Markdown string template using the date stamp pattern already present (`${new Date().toISOString().split('T')[0]}`).

### Data Flow

```
Caller code
  → TemplateService.getArchitectTemplate()
    → returns [5 file metadata entries]

Caller code
  → TemplateService.getArchitectTemplateContent('04_SPECIFICATION.md')
    → returns Markdown string with structured spec content

Caller code
  → TemplateService.getSpecificationTemplate()
    → returns [{ key: '04_SPECIFICATION.md', title: 'Execution Specification', required: true }]

Caller code
  → TemplateService.getSpecificationTemplateContent('04_SPECIFICATION.md')
    → returns Markdown string (same content as Architect 04_SPECIFICATION.md)
```

### Error Handling

- `getArchitectTemplateContent()` returns empty string for unknown keys (unchanged behavior)
- No validation needed — template content is static strings, not user input
- No database interaction in template content generation

### Alternatives Considered

- **Option B: Template content as separate Markdown files** — Rejected because it adds file I/O and breaks the current in-memory pattern. Keeping content as template strings keeps the service self-contained and fast.
- **Option C: Generate content dynamically from a section schema** — Rejected as over-engineering for 5 static templates. The content varies too much between sections for a generic renderer.

## Security Considerations

- No user input is interpolated into templates beyond the date stamp (safe)
- No SQL queries, no file system access
- No new dependencies

## DB Changes

None. No migration required.

## API Contract

No new endpoints. The existing behavior is preserved:
- `GET /api/v1/templates/types` (if it exists) will now include the new `SPECIFICATION` type
- The frontend template picker will show `04_SPECIFICATION.md` as part of the Architect template set
- Backward compatible — any caller that ignores extra entries in `ARCHITECT_TEMPLATE_FILES` continues to work
